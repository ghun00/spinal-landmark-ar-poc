## 3. Challenge와 해결 과정

각 항목은 **증상 → 근거(측정) → 해결 → 검증** 순서로 정리.

### C1. 실물 스티커·촬영 영상이 없는 상태에서 개발

- **상황**: 스티커 색·크기 미정, 실제 촬영 영상 없음.
- **해결**: Python으로 합성 장면 생성기(`reference/synth.py`)를 만들고, 정상·작은 스티커·어두움·회전·가로·가림·빨간 물체 추가·빨간 사각형·잘못된 배치·주황 물체 10종으로 시작.
- **검증 장치**: 같은 장면을 Python과 OpenCV.js에 넣어 중심 좌표를 비교하는 동등성 테스트. 결과 **0px 차이**.
- **회고**: 합성 장면의 "피부"는 채도가 실제보다 낮았다(S≈83). 이것이 나중에 C6의 원인을 놓친 이유. 이후 실측값을 받을 때마다 그 조건을 합성 장면으로 추가하는 방식으로 보완.

### C2. Python ↔ 브라우저 동등성 확보 중 기술 문제

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| 테스트 이미지가 35MB | 노이즈 때문에 압축이 안 됨 | 64px 노이즈 타일 반복 + 원본 RGBA를 gzip으로 저장, PNG는 git 제외(생성기로 재생성) → 약 2MB |
| 실행할 때마다 테스트 이미지가 달라짐 | Python `hash()`가 실행마다 무작위 | `zlib.crc32`로 시드 고정 |
| Node에서 opencv.js 로딩 실패 | `package.json`의 `"type":"module"` 때문에 UMD 파일이 ESM으로 해석됨 | `vm`으로 CommonJS 래퍼를 씌워 로딩 |
| 축소 크기가 1px 다를 수 있음 | Python `round()`는 은행가 반올림 | 양쪽 모두 `floor(x+0.5)`로 통일 |

### C3. 최종 코드 리뷰에서 나온 실사용 버그

| 문제 | 근거 | 해결 |
| --- | --- | --- |
| 카메라 "다시 시도"를 누를 때마다 검출이 중복 실행 | 브라우저에서 재현: 초당 30회 → 3번 재시도 후 82회 | 카메라 세션 번호를 두어 이전 세션의 프레임 콜백은 즉시 종료 |
| 느린 네트워크에서 OpenCV 로딩을 30초 후 "실패"로 표시 | 11MB 파일 + WASM 컴파일 | 30초 후에는 "느립니다" 안내만 하고 계속 대기, 실제 오류일 때만 실패 처리 |
| 화면이 꺼졌다 켜지면 영상이 멈출 수 있음 | 백그라운드 복귀 처리 없음 | 화면이 다시 보이면 `video.play()` |

### C4. Vercel 배포 실패 → 404

1. **`PYTHON_ENTRYPOINT_NOT_FOUND`**
   - 원인 추정: `reference/requirements.txt`를 보고 Python 프로젝트로 판단.
   - 해결: `vercel.json`에 `framework: null`, 설치·빌드 명령 없음을 고정해 대시보드 설정보다 우선하게 함. 같은 버전의 Vercel CLI로 로컬에서 실패 재현 → 수정 후 성공 확인.
2. **배포 성공인데 모든 경로 404**
   - 원인: Vercel 프로젝트의 **Root Directory가 `reference`**로 설정돼 있었음(프로젝트 이름도 `reference`). 그 폴더는 `.vercelignore`로 제외되므로 배포 파일이 0개.
   - 해결: Root Directory를 비우고 재배포(사용자가 직접 설정).
   - **회고**: 첫 번째 오류도 같은 원인이었을 가능성이 큼. 대시보드 설정을 먼저 확인했으면 한 번에 끝났을 것.

### C5. UI: 메시지 길이에 따라 화면이 깜빡임

- **증상**: 상단 안내 문구가 두 줄로 넘어가면 카메라 화면 높이가 바뀌어 깜빡이는 느낌.
- **해결**: 안내를 카메라 화면 하단의 **떠 있는 토스트**로 바꿔 레이아웃에서 분리. 정상 인식 중에는 숨김.
- **함께 바뀐 UI**(사용자 요청)
  - 화면 정지 버튼 삭제(휴대폰 거치 예정)
  - 좌측 상단에 반투명 `마커 n/3` 태그
  - 하단 면책 문구 삭제
- **검증**: 메시지를 바꿔 가며 캔버스 높이를 측정 → 값이 하나로 유지됨.

### C6. "스티커 3개인데 후보 과다" — 피부가 빨강으로 잡힘

- **근거**(S25 디버그 화면 + 테스트 사진 분석)

  | | H | S |
  | --- | --- | --- |
  | 스티커 | 177–178 | 161–162 |
  | 피부 | 7–9 | 102–118 |
  | 기존 기준 | 0–10 | ≥ 100 ← 피부가 통과 |

  등 전체가 빨강 영역이 되어 PSIS 스티커가 피부 덩어리에 묻혔고, 피부 얼룩 하나가 4번째 후보가 됨.
- **해결**
  - 채도 하한 100 → **140**. 사진에서 기준을 바꿔 보니 130부터 피부가 사라졌고, 스티커는 161이라 그 중간을 택함.
  - 화면 가장자리에 닿는 빨간 물체는 제외(`edge`). 사진 맨 위에 잘린 귀가 후보로 잡혔기 때문.
- **검증**: 실측 피부색으로 만든 `warm_skin` 장면과 `edge_red` 장면 추가. 이전 설정이 `warm_skin`에서 실패하는 것까지 확인.

### C7. 멀리서는 인식이 안 됨

- **근거**: 사진을 단계적으로 축소해 거리를 흉내 냄. 기존 설정은 스티커 지름 약 **17px 미만**에서 놓침.
  - 640px로 줄여서 처리 → 잡티 제거(5px)가 작은 스티커를 깎아냄 → 남은 것은 최소 면적 기준에 걸림.
- **해결**: 축소 없이 원본 해상도로 처리(1280), 잡티 제거 3px, 최소 면적 비율 2e-5 → 지름 약 **9px까지** 인식.
- **대가**: 데스크톱 기준 프레임당 5ms → 18ms. S25는 약 20fps로 예상(실측 아님).
- **검증**: 9px 스티커 장면 `far_warm` 추가. 이전 설정에서 실패 확인.
- **한계**: 9px 미만에서는 스티커 색이 피부와 섞여 채도가 떨어짐. 설정으로는 한계라 큰 스티커(지름 2cm 이상) 권장.

### C8. 인식이 깜빡임 → 고정형 / 실시간형

- **증상**: 매 프레임 다시 검출하므로 경계 조건에서 잡혔다 안 잡혔다 반복.
- **사용자 결정**: 3개가 잡히면 그 시점 위치를 유지하고, 틀리면 "다시 분석"으로 재시도.
- **해결 — 고정형**
  - 3개 마커가 **연속 5프레임**, 프레임 높이의 1% 이내로만 움직이면 평균 위치로 고정하고 검출 중지(영상은 계속 실시간).
  - 한 프레임 오검출로 잘못 고정되는 것을 막기 위해 "안정 구간"을 둠.
  - 태그: `마커 3/3 · 확인 중` → `마커 3/3 · 고정됨`. [다시 분석] 버튼.
- **해결 — 실시간형**: 우측 상단 토글. 이전 동작(매 프레임 재인식, 하나라도 빠지면 즉시 숨김). 선택은 기기에 기억.
- **명세와의 차이**: 원래 명세의 "마커가 없으면 즉시 숨김" 규칙은 고정 전(인식 중)과 실시간형에만 적용. README "명세 대비 변경"에 기록.

### C9. 그림자진 피부 가장자리 오검출 — 정확도 개선

- **근거**(S25 디버그 화면 2장)

  | | H | S | 원형도 |
  | --- | --- | --- | --- |
  | 스티커 6개 | 176–179 | 169–181 | 0.85–0.92 |
  | 오검출(팔·겨드랑이 그림자 가장자리) | 7–10 | 140–162 | 0.71–0.78 |

  채도·밝기는 겹치고, **색상과 원형도**가 갈림.
- **해결**: 낮은 빨강 범위 상한 10 → **5**, 원형도 하한 0.70 → **0.80**. 진짜 스티커는 모든 테스트에서 0.83 이상.
- **검증**: 두 종류 오검출을 모두 재현한 `shadow_skin` 장면 추가(이전 설정 8개 → 현재 3개).

### C10. 밀집된 후보 제외 — "마커는 discrete한 점"

- **사용자 아이디어**: 너무 모여 있는 것은 후보에서 빼자. 마커는 떨어진 점이니까.
- **근거**: 오검출 후보 주변에는 작은 빨간 점이 약 6개 몰려 있었고, 진짜 스티커 주변은 깨끗함.
- **시도 1 — 주변 빨간 픽셀 비율**: 점 크기에 따라 값이 크게 달라져 기준을 정하기 어려움 → 폐기.
- **시도 2 — 주변 빨간 점 개수**(채택)
  - 잡티 제거 전 마스크의 연결 영역을 "빨간 점"으로 보고, 후보 반지름의 5배(최소 +12px) 안에 **다른 점이 3개 이상**이면 `clutter`로 제외.
  - 실측: 진짜 스티커 주변 점은 모든 장면·거리에서 **0개**. 스티커끼리 붙은 `bad_layout`이 최대 2개라 허용 범위.
- **검증**: 스티커와 **같은 색**의 점 무리 장면 `cluster` 추가. 색으로는 걸러지지 않고 이 규칙으로만 제외됨. 속도 변화 없음(약 18ms).

## 4. 현재 검출 파이프라인과 설정

```
카메라 프레임(720×1280)
 → HSV 변환 → 빨강 범위 2개 OR
 → [잡티 제거 전 마스크로 빨간 점 목록 작성]
 → 잡티 제거(열기·닫기, 3px)
 → 외곽선마다:
    가장자리 닿음 → edge
    너무 작음/큼  → small / large
    원형도 < 0.80 → circularity
    주변 빨간 점 > 2개 → clutter
    나머지 → 후보
 → 후보가 정확히 3개 + C7이 PSIS보다 충분히 위 → C7 / L-PSIS / R-PSIS
 → P = C7 + r × (PSIS 중간점 − C7)
 → 고정형: 5프레임 안정 시 고정 / 실시간형: 매 프레임 갱신
```

`config/detection.json` (2026-11-08 기준)

| 항목 | 값 | 처음 값 | 바뀐 이유 |
| --- | --- | --- | --- |
| `hsvRanges` | H 0–5 ∪ 160–180, S ≥ 140, V ≥ 80 | H 0–10 ∪ 170–180, S ≥ 100, V ≥ 70 | 피부(C6), 그림자(C9) |
| `processLongSide` | 1280 | 640 | 원거리(C7) |
| `morphKernel` | 3 | 5 | 원거리(C7) |
| `minAreaFrac` | 0.00002 | 0.00005 | 원거리(C7) |
| `minCircularity` | 0.80 | 0.70 | 그림자 조각(C9) |
| `clutterRadius` / `clutterRadiusMinPx` / `maxNeighbors` | 5 / 12 / 2 | — | 밀집 제외(C10) |
| `minVerticalGapFrac` | 0.10 | 0.10 | — |

## 7. 배운 점

1. **추측보다 측정.** "후보 과다"의 원인을 추측하는 대신 진단 화면에 HSV를 띄워 받은 숫자 한 장으로 바로 해결됐다. 진단 화면은 처음부터 만드는 게 좋다.
2. **합성 데이터는 실측으로 계속 보정해야 한다.** 첫 합성 피부는 실제보다 채도가 낮아 문제를 숨겼다. 실측값을 받을 때마다 회귀 장면으로 고정했다.
3. **한 가지 특징에 기대지 않는다.** 색(H·S), 모양(원형도), 위치(가장자리), 주변 맥락(밀집)이 각각 다른 종류의 오검출을 막는다.
4. **도메인 지식이 가장 강한 규칙이 된다.** "마커는 떨어진 점"이라는 사용자의 관찰이 색으로 구분 안 되는 경우까지 막는 규칙이 됐다.
5. **배포 문제는 코드보다 설정을 먼저 본다.** Vercel 404는 Root Directory 설정 하나 때문이었다.
6. **사용 방식이 요구사항을 바꾼다.** 휴대폰 거치라는 실제 사용 방식이 정지 버튼 삭제와 고정형 추가로 이어졌다. 명세와 달라진 점은 README에 기록해 두었다.
